# Решения и допущения

- Одна компания, одна роль на пользователя. Постановщиков может быть несколько: все видят и редактируют все объекты и задачи. Исполнителем может быть только пользователь с ролью executor.
- Постановщик может редактировать название, описание, объект и исполнителя в любом статусе. Редактирование не сбрасывает статус. После переназначения прежний исполнитель сразу теряет доступ к задаче и её истории. Для принятой задачи повторное открытие не предусмотрено.
- Удаление объекта удаляет его задачи и историю каскадно; удаление задачи удаляет её историю. Это осознанное толкование права постановщика удалять задачи. Самостоятельные операции INSERT/UPDATE/DELETE над историей запрещены обоим ролям. Если история должна сохраняться после удаления задачи, нужно согласовать архивирование вместо физического удаления.
- История фиксирует создание задачи и каждую смену статуса; редактирование остальных полей не фиксируется, поскольку это не требовалось. Имя автора события сохраняется снимком.
- Исполнитель видит только собственные задачи даже на общем объекте. Имена постановщиков доступны только в контексте назначенных ему задач; список всех сотрудников скрыт.
- Обязательный комментарий требуется только для доработки; интерфейс запрашивает его при возврате. RPC допускает комментарии к остальным переходам.
- Одновременная смена статуса проверяется по ожидаемому предыдущему значению. При конфликте пользователь получает сообщение об обновлении задачи; автоматического повторения действия нет.
- Пустые объекты видны только постановщикам. Готовность объекта — доля принятых задач среди доступных текущему пользователю. Это показатель задач, не физической готовности стройки.
- Удаление учётных записей, управление ролями и регистрация находятся вне клиентского интерфейса. Профили создаёт только администратор. Пароли не хранятся в таблицах CRM.
- Для постановщика раздел «Все задачи» показывает задачи всей команды. Исполнитель видит «Мои задачи» только со своими назначениями. После сохранения задачи открывается её карточка; фильтры сбрасываются. Исполнители не получают прав постановщика даже через прямой API.
- Демо — отдельный режим без Supabase-конфигурации. Роли выбираются явно, данные находятся в localStorage. Демо не выдаётся за защищённую рабочую среду.

## Подключённая рабочая среда

Supabase-проект susuopetvkuliqxixnnx: миграция применена, публичная регистрация отключена, Email Auth включён. Созданы реальные аккаунты: 1 постановщик и 2 исполнителя. В базе — 3 объекта и 6 задач в разных статусах. Пароли передаются отдельно и не входят в репозиторий.

Результат прямых HTTP-проверок: SECURITY-VERIFICATION.md. Эти проверки используют только публичный ключ и обычные сессии пользователей. Дополнительно SQL-правила проверяются локально через PGlite. Секретный admin ключ применялся только при первичном создании пользователей; его временный файл удалён.

Для повторного запуска в другом облачном проекте необходимо отдельно применить миграцию, создать пользователей и отключить регистрацию. Live-обновления, вложения к задачам, сроки, уведомления, пагинация и восстановление удалённых данных не включены в объём ТЗ. Фотографии объектов добавлены отдельно по дополнительному запросу.

## Фотографии объектов — дополнительная функциональность

- Фотографии не требовались исходным ТЗ и добавлены по дополнительному запросу. Постановщик может загрузить несколько файлов при создании и редактировании объекта. Первая фотография становится обложкой; удаление фотографии из формы применяется при сохранении.
- Приняты ограничения: до 10 фотографий на объект, JPEG/PNG/WebP, до 5 МБ на файл. Размер, MIME-типы и количество ограничены также на стороне Supabase. База проверяет принадлежность пути фотографии папке соответствующего объекта.
- Используется приватный бакет `object-photos`. Загрузка и удаление разрешены только постановщикам. Исполнитель читает фотографии только объектов, доступных ему по назначенным задачам. Замена создаёт новый случайный путь, перезапись существующего файла не разрешена. Скачанные пользователем копии невозможно отозвать.
- В карточке объекта первая фотография показана крупнее остальных; остальные имеют одинаковый размер. Галерея адаптируется к узкому экрану. Fancybox открывает снимки крупно и позволяет переключаться между ними.
- Тестовые объекты дополнены минимум до четырёх иллюстративных фотографий. Для новых объектов загрузка фотографий необязательна; требование о четырёх снимках относится к наполнению тестовых объектов, а не к обязательной валидации формы.
- Для развёртывания нужны миграции `202611050003_object_photos.sql` и `202611050004_photo_policy_qualification.sql` после основных миграций. В подключённом тестовом проекте они применены. Результаты девяти реальных проверок Storage приведены в `STORAGE-VERIFICATION.md`.
- Fancybox подключён через `@fancyapps/ui` 6.x. Согласно [условиям производителя](https://fancyapps.com/pricing/), бесплатная оценка разрешена в development и staging. Тестовое задание рассматривается как оценочная среда. Перед использованием в production нужно приобрести подходящую лицензию или заменить библиотеку. Лицензия в рамках задания не приобреталась.

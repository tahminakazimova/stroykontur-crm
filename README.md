# СтройКонтур — мини-CRM «Объекты и задачи»

React 19 + TypeScript + Vite + Supabase. Объекты, задачи, две роли, строгий цикл статусов, история и доступ на уровне PostgreSQL.

Приложение: https://stroykontur-crm-tahmina.pinkguppy.chatgpt.site
GitHub: https://github.com/tahminakazimova/stroykontur-crm

## Быстрый запуск

Нужен Node.js 22+.

```sh
npm ci
cp .env.example .env.local
npm run dev
```

В `.env.example` находятся только публичные URL и publishable key подключённого тестового Supabase-проекта. Они разрешены для браузера: данные защищаются RLS и пользовательской сессией. Пароли тестовых пользователей передаются отдельно; их нет в репозитории. Публичная регистрация в облачном проекте отключена.

Чтобы использовать отдельную базу, замените значения VITE_SUPABASE_URL и VITE_SUPABASE_ANON_KEY на собственные. Если обе переменные пусты, приложение запускается в явно отмеченном деморежиме: роли выбираются кнопками, данные находятся в localStorage. Демо не предназначено для реальных данных.

## Проверка и сборка

```sh
npm test
npm run build
```

Локальные тесты выполняют настоящую SQL-миграцию в PostgreSQL (PGlite), переключают authenticated/anon и auth.uid(). Проверяются в том числе 50 сочетаний роли и статусов, чужие данные, права истории, неизменяемость автора/даты и переназначение.

Для повторения реальных HTTP-тестов подготовьте **вне репозитория** JSON с тремя тестовыми аккаунтами: массив `{ "role": "manager" | "executor", "email": "...", "password": "..." }`. Нужен 1 постановщик и 2 исполнителя. Проверки создают отдельные объекты с префиксом API QA и в конце удаляют только эти объекты. Существующие задачи не меняются. Admin/service_role ключ не используется.

```sh
TEST_CREDENTIALS_FILE=/absolute/private/accounts.json npm run test:api
```

Отчёт реального запуска: [docs/SECURITY-VERIFICATION.md](docs/SECURITY-VERIFICATION.md).

## Развёртывание на собственном Supabase

1. Создайте пустой Supabase-проект.
2. Примените все миграции из `supabase/migrations/` по порядку через SQL Editor или `supabase db push` после привязки CLI:
   - `202611050001_crm.sql` — таблицы CRM, роли, RLS, статусы и история;
   - `202611050002_rpc_conflict_http.sql` — HTTP 409 при конфликте статуса;
   - `202611050003_object_photos.sql` — фотографии объектов и приватный бакет Storage;
   - `202611050004_photo_policy_qualification.sql` — уточнение политики чтения фотографий.
   Для новой базы нужны все четыре миграции. Если первые две уже применены, выполните только третью и четвёртую. Не запускайте применённые SQL-файлы повторно вручную.
3. В Auth → Sign In / Providers выключите **Allow new users to sign up**. Email/password оставьте включённым. `supabase/config.toml` относится к локальному Supabase и сам по себе облачные настройки не меняет.
4. Создайте пользователей вручную через Auth → Users и добавьте соответствующие UUID в `public.profiles(id,name,role)` через SQL Editor. Допустимые роли: manager и executor.
5. Для первоначального наполнения можно локально выполнить `node scripts/seed.mjs` с переменными SUPABASE_URL, SUPABASE_ANON_KEY и SUPABASE_SERVICE_ROLE_KEY. Последняя переменная принимает серверный secret/service_role ключ. Скрипт предназначен для новой базы; повторный email вызывает остановку. Он создаёт 3 аккаунта со случайными паролями, 3 объекта и 6 задач, проводя их через реальные переходы от имени пользователей. Сохраните выведенные пароли приватно. Переменная SEED_CREDENTIALS_FILE позволяет сохранить их в отдельный приватный JSON вместо stdout.
6. Настройте `.env.local`, затем соберите и разверните `dist/`.

Для Vercel/Netlify: команда `npm ci && npm run build`, каталог `dist`. На сборке задайте только две публичные VITE_ переменные. Приватные ключи не должны иметь префикс VITE_, попадать в frontend, GitHub или логи сборки.

## Фотографии объектов

Постановщик может загрузить фотографии при создании или редактировании объекта, а также кнопкой «Добавить фотографии» в его карточке. Поддерживаются JPEG, PNG и WebP, до 5 МБ на файл и до 10 фотографий на объект. Первая фотография служит обложкой. В карточке объекта фотографии отображаются галереей; Fancybox позволяет открыть изображение крупно, увеличить его и переключаться между снимками.

Файлы хранятся в приватном бакете Supabase Storage `object-photos`, ссылки на них — в `objects.photo_paths`. Постановщик управляет фотографиями; исполнитель может читать фотографии только доступных ему объектов. Анонимное чтение запрещено. Уже скачанную пользователем копию файла отозвать невозможно.

Для трёх тестовых объектов добавлены иллюстративные фотографии зданий. Скрипт `scripts/seed-photos.mjs` дополняет галереи существующих объектов до четырёх снимков, сохраняя имеющиеся; он использует обычную сессию постановщика. Источники исходных иллюстраций перечислены в `docs/IMAGE-CREDITS.md`.

Проверка Storage использует тот же приватный файл аккаунтов, что и API-тесты, и создаёт отдельные временные данные:

```sh
TEST_CREDENTIALS_FILE=/absolute/private/accounts.json STORAGE_TEST_REPORT=docs/STORAGE-VERIFICATION.md node --env-file=.env.local scripts/test-storage.mjs
```

Результат: [9 проверок реального Storage](docs/STORAGE-VERIFICATION.md). Эти проверки дополняют основные SQL- и API-тесты.

В проекте используется `@fancyapps/ui` 6.x. Производитель разрешает бесплатное ознакомление в средах разработки и staging. Тестовое задание используется для такой оценки; перед эксплуатацией в production необходимо приобрести подходящую лицензию либо заменить библиотеку. Лицензия в рамках этого задания не приобреталась. ## Защита

- RLS включён для profiles, objects, tasks, task_history; анонимное чтение запрещено.
- Исполнитель читает только назначенные ему задачи, их объекты и историю. Чужие задачи скрыты даже внутри общего объекта.
- Роли хранятся в таблице profiles, закрытой для записи клиентскому API. Они не берутся из редактируемых метаданных пользователя.
- BEFORE-триггер проверяет роль, назначение, поля, автора/дату и переходы статуса, включая прямые REST UPDATE.
- RPC transition_task работает с правами вызывающего и ожидаемым предыдущим статусом, предотвращая повторное применение конкурирующих действий.
- AFTER-триггер создаёт историю в той же транзакции. Автор — auth.uid(), время — серверное. Через API история доступна только для чтения.
- Узкие SECURITY DEFINER функции имеют пустой search_path и явные ссылки на схемы. Прямой вызов триггерных функций запрещён.
- Удаление задачи/объекта постановщиком каскадно удаляет соответствующую историю. Самостоятельные записи, изменения и удаления истории через API запрещены. Если аудит должен переживать удаление задачи, требуется архивирование — это отдельное согласуемое изменение.

Статусы: new → working → review → accepted либо review → revision → working. Управление ролями, пользователями и восстановление паролей находятся вне клиентского интерфейса.

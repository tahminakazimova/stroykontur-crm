# СтройКонтур — мини-CRM «Объекты и задачи»

React 19 + TypeScript + Vite + Supabase. Интерфейс на русском. Объекты, задачи, 2 роли, строгий цикл статусов, автоматическая история, RLS. Есть явный браузерный деморежим для просмотра без облачного проекта.

## Запуск

Нужен Node.js 22+.

```sh
npm ci
cp .env.example .env.local
npm run dev
```

Без значений в `.env.local` открывается **демо**. Нажмите на одного из трёх пользователей. Изменения сохраняются в браузере, вход — в текущей вкладке. Это не защищённый сервер: не вводите реальные данные. «Сбросить демо» возвращает пример.

## Подключение настоящего Supabase

1. Создайте пустой проект Supabase. В SQL Editor выполните `supabase/migrations/202611050001_crm.sql` (либо `supabase db push` после привязки CLI).
2. В Auth → Sign In / Providers отключите **Allow new users to sign up**. Email/password оставьте включённым. `supabase/config.toml` отключает регистрацию только для локального Supabase, а не автоматически для облачного проекта.
3. Заполните `.env.local`:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_PUBLISHABLE_OR_ANON_KEY
```

4. Создайте пользователей и данные скриптом ниже. Он рассчитан на новую базу; при повторном email останавливается, а не меняет существующую учётную запись. В случае частичного сбоя сначала проверьте пользователей и данные в панели Supabase.

```sh
# Задайте через локальное окружение, не сохраняйте секреты в репозитории.
export SUPABASE_URL='https://YOUR_PROJECT.supabase.co'
export SUPABASE_ANON_KEY='YOUR_PUBLIC_KEY'
# SUPABASE_SERVICE_ROLE_KEY задаётся только локально и используется только этим скриптом.
node scripts/seed.mjs
```

Скрипту также нужна переменная `SUPABASE_SERVICE_ROLE_KEY`. Введите её безопасным способом в локальной оболочке. Скрипт создаёт постановщика и двух исполнителей, генерирует случайные пароли, создаёт 3 объекта и 6 задач и проводит их через настоящие переходы с соответствующими пользователями. Сохраните напечатанные доступы отдельно и передайте проверяющему приватно.

Ручной вариант: создайте пользователей через Supabase Auth → Users, затем в SQL Editor добавьте строки `public.profiles(id, name, role)` с UUID из Auth. Роли: `manager`, `executor`. Регистрация и изменение ролей через клиентский API недоступны.

## Проверка и сборка

```sh
npm test
npm run build
```

Тесты запускают миграцию в PostgreSQL (PGlite), переключают роли authenticated/anon и auth.uid(), проверяют чтение чужих данных, запрет изменения содержимого исполнителем, переходы, обязательный комментарий, неизменяемость автора/даты, права истории и удаление. Облачный Supabase требует отдельного smoke-теста.

Разверните `dist/` на Vercel/Netlify/статическом хостинге. Настройки сборки: `npm ci && npm run build`, каталог `dist`. На хостинге добавьте только две публичные `VITE_` переменные и пересоберите. Service role, access token и пароль БД никогда не должны иметь префикс VITE_ или попадать в клиент, репозиторий, логи сборки.

## Как устроена защита

- RLS для всех четырёх таблиц; анонимное чтение запрещено. Исполнитель читает только свои задачи и связанные объекты/историю.
- Роли берутся из закрытой для записи таблицы profiles, а не из редактируемых метаданных пользователя.
- BEFORE-триггер проверяет статус, роль, назначение, неизменяемость автора и даты, поля задачи. Он срабатывает и при прямом REST UPDATE.
- RPC transition_task использует права вызывающего и ожидаемый статус для защиты от конфликтов. Триггер проверяет те же ограничения независимо от RPC.
- AFTER-триггер пишет историю в той же транзакции; API-пользователям выдан только SELECT истории. Автор события всегда auth.uid(), дата — серверная.
- SECURITY DEFINER используется только в узких функциях с фиксированным пустым search_path; напрямую вызывать триггерные функции через API запрещено. is_manager не принимает чужой user ID.
- Администратор БД и service_role остаются доверенными операторами: их секреты нельзя выдавать пользователю.

Схема: profiles → tasks (исполнитель, автор), objects → tasks → task_history. Индексы есть по assignee_id, object_id и task_id/created_at. Перечень статусов: new → working → review → accepted либо review → revision → working.
